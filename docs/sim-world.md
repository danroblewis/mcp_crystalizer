# The sim world, part 2: scenario data

`sim/world.py` builds the original, byte-identical 10-incident world (4 services, 8 people, 10
channels, 8 pages) exactly as before. Right before it returns, one hook call --
`scenarios.extend(data, ERRORS, seed=seed)` -- appends a second, larger layer generated by
`sim/scenarios.py` with its own seeded RNG stream (`random.Random(seed * 1000 + 1)`), so the
original part never reorders or re-seeds. `sim/world.py`'s `build_repo()` then commits the new
incidents into the same git repo, after the original 11 commits (see "The git history" below).

This file is the map: what each archetype is, how its entities cross-link, and where to start
exploring. `INC-001..INC-010` are the original incidents; `INC-011..INC-050` are scenario incidents.

## The new world, roughly

- **8 teams**: the original 4 (`payments`, `storefront`, `supply`, `platform`) plus 4 new ones
  (`identity`, `eventbus`, `search`, `billing`), each with its own ~10-person roster.
- **15 services**: the original 4 plus 11 new ones, owned entirely by the 4 new teams:
  - `identity`: `auth-service`, `sso-gateway`, `directory-service`
  - `eventbus`: `event-bus`, `webhook-dispatcher`, `stream-processor`
  - `search`: `search-api`, `indexer`, `autocomplete-service`
  - `billing`: `billing-service`, `invoicing`

  New incidents only ever land on these 11 services -- never on the original 4 -- so nothing about
  the original incidents' git history, metrics, logs, or Jira/Slack search results can shift.
- **50 incidents** total: the original 10 plus 40 new ones split across the archetypes below.
- **50 confluence pages**: the original 8, 11 new runbooks (one per new service), 4 new team
  on-call guides, 6 architecture pages, 6 postmortems, and 15 generic filler/reference pages.
- **`world.deploys`**, **`world.oncall_rotations`**: two new top-level lists/maps, see below.

## Archetypes and where to look

### 1. Cascading multi-service incidents (5 groups, 15 incidents)

One upstream incident's errors surface a few minutes later as elevated errors in two downstream
services. All three share one real trace id (the causal thread); each downstream incident also
carries 1-2 unrelated "red herring" trace ids.

- **Start at `INC-011` (`AUTH-106`, auth-service)** -- the upstream incident. Its
  `child_incidents` are `["INC-012", "INC-013"]`; its `jira.issuelinks` have `type: causes` entries
  for both children; its `pagerduty.related_incidents` list both downstream PagerDuty ids.
- **`INC-012` (`SSO-103`, sso-gateway)** and **`INC-013` (`DIR-102`, directory-service)** each have
  `parent_incident: "INC-011"` and one `jira.issuelinks` entry `{"type": "is caused by", "key":
  "AUTH-106"}`. Their own Slack thread lives in their *team's* `#<team>-alerts` channel (not
  `#incidents`) and says "Same root cause as INC-011 (AUTH-106), see <permalink>"; the upstream
  thread in `#incidents` gets a reply back from each downstream owner with a permalink of its own.
- `INC-011..013` share one trace id across their `trace_ids` arrays and log lines -- that's the
  thread an extractor should actually follow; the rest are decoys.
- The other four groups: `event-bus -> {webhook-dispatcher, stream-processor}`,
  `search-api -> {indexer, autocomplete-service}`, `billing-service -> {invoicing, auth-service}`,
  and `directory-service -> {event-bus, search-api}` (this last one is the one cross-team bridge
  that ties the `identity`/`billing` cluster to the `eventbus`/`search` cluster in the
  documentation graph -- see "Reachability" below).

### 2. Repeat incident pairs with postmortems (6 pairs, 12 incidents + 6 pages)

Same service, same `error_class`, 3-8 weeks apart -- the first fix didn't hold.

- **Start at `INC-026` (`AUTH-117`)** and its repeat, **`INC-027` (`AUTH-122`)**, 21-56 days later
  (`second.repeat_of == first.id`). `INC-027`'s Jira description and its own first Slack message
  both say "This looks like AUTH-117 again". Confluence page **`50021`, "auth-service postmortem:
  AuthTokenExpired recurrence"** has
  `parent_id` set to the `auth-service` runbook page and `links` containing both Jira keys, both
  commit shas, and the `identity` architecture page id.
- The other five pairs live on `event-bus`, `webhook-dispatcher`, `search-api`, `billing-service`,
  and `invoicing`.

### 3. Escalated-from-team-channel incidents (6 incidents)

- **`INC-038` (`SSO-112`, sso-gateway)**: 15-30 minutes of uncertain triage happens first in
  `#identity-alerts` (a real Slack thread, `thread_ts` in `inc["escalation"]["team_thread_ts"]`),
  ending with "Moving this to #incidents, see <permalink>". The canonical `#incidents` thread's
  first message opens with "Continuing from #identity-alerts, see <permalink>" -- both permalinks
  are real, resolve to the other thread, and are stored explicitly: `inc["escalation"] =
  {team_channel, team_thread_ts, permalink}` and `inc["slack"]["escalated_from_permalink"]`.
- The team-channel thread is stored in `world["noise"]["slack"]` (a channel message list, same as
  the original noise), not inside the incident -- it is a real, independent `(channel, thread_ts)`
  pair a Slack search or `conversations_replies` call will find on its own.

### 4. Deploy-preceded incidents (3 incidents)

- **`INC-044` (`AUTH-130`)**: `world.deploys` gets a new entry, e.g. `DEP-001`, a bot message in
  `#deploys` ("Deployed auth-service@\<sha\> to prod") 5-25 minutes before the incident starts.
  `INC-044.deploy_id == "DEP-001"` and `deploys["DEP-001"].sha == INC-044.commit` exactly (the
  deploy *is* the incident's own commit reaching prod). The incident's first Slack message quotes
  the deploy's permalink directly instead of only guessing a suspect commit.
- The Slack sim serves `#deploys` messages generically (`slack.conversations_history` /
  `conversations_replies` / `conversations_search_messages` on channel `#deploys` all see them).

### 5. Still-open incidents (4 incidents)

- **`INC-047` (`EVT-129`, event-bus)**: `jira.status` is `"In Progress"`, `pagerduty.status` is
  `"triggered"`, `pagerduty.resolved_at` is `null`, and the Slack thread's last message is "Still
  digging into this one, no root cause yet" -- no rollback, no resolution, and (deliberately) no
  postmortem page exists yet.

### 6. Long threads with red herrings (an overlay on 8 of the above)

- **`INC-012` (`SSO-103`)** (one of the cascade downstreams) has, appended near the middle of its
  thread: a message naming a real-but-wrong commit sha borrowed from a different incident on the
  same service ("Wait, might be \<sha\> -- that also touched sso-gateway recently"), a message with
  a trace id copy-pasted from a *different* incident's own `trace_ids` (never in this incident's own
  logs), and a retraction ("False alarm on that other commit, that's unrelated to this one").
  Find the other 7 by searching incident threads for `"false alarm"`.

### 7. Cross-referencing Jira comments (15 incidents)

- **`INC-011` (`AUTH-106`)**: `jira.comments` is a real 3-4 entry array (`jira_get_issue_comments`
  returns it verbatim); one comment quotes a Slack permalink, and -- because `INC-011` is a cascade
  upstream -- another names the downstream tickets it's "causing". Applied to the 5 cascade
  upstreams, the 6 repeat-pair second incidents, and 4 of the 6 escalations.

### 8. On-call rotations (`world.oncall_rotations`, one list per team)

- `oncall_rotations["identity"]` is a list of `{person, start, end}` 45-day windows covering the
  whole simulated period; the same 3 people cycle through it. Every new incident's
  `jira.assignee`/`pagerduty.assignee` is whoever's window covers `started_at` for that team --
  check `INC-026` and `INC-027` (the `auth-service` repeat pair, ~a month apart): if their gap
  crosses a rotation boundary, they have different owners despite being the same underlying bug.
  The original 4 teams also get a (single-window, informational-only) rotation entry so
  `world.oncall_rotations` covers all 8 teams uniformly; the original 10 incidents predate this
  feature and are not required to match it.

### 9. Runbook -> architecture -> postmortem web (6 architecture pages)

- **`50015` "Identity architecture"**, **`50016` "Eventbus architecture"**, **`50017` "Search
  architecture"**, **`50018` "Billing architecture"** each `links` to every runbook (and the
  on-call guide) for services on that team; every one of those runbooks lists the architecture page
  back in its own `links`. **`50019` "Payments & billing integration architecture"** and **`50020`
  "Event-driven platform architecture"** are the two cross-team pages: they each pull in runbooks
  from two different new teams, plus one runbook from the *original* four services (`payments-api`
  and `notifier` respectively) -- referenced, never modified, just so the whole documentation graph
  is walkable from an original runbook into the new material. Every repeat-pair postmortem also
  lists its team's architecture page in `links`, and the architecture page lists the postmortem
  back.

### 10. Noise (10+ messages)

- Extra `#general`/`#team-*`/misc-channel chatter reusing incident vocabulary ("anyone else seeing
  timeouts", "rate limited", a stale-looking fake trace id) with no linked Jira/PagerDuty/Confluence
  entity at all -- appended to `world["noise"]["slack"]` after the original 30 noise messages.

## New fields, at a glance

| Field | On | Meaning |
|---|---|---|
| `parent_incident` / `child_incidents` | incident | cascade linkage |
| `repeat_of` | incident | points at the earlier incident of a repeat pair |
| `escalation` / `slack.escalated_from_permalink` | incident | team-channel pre-discussion pointer |
| `deploy_id` | incident | points into `world.deploys` |
| `jira.issuelinks` | incident.jira | `[{type, key}]`, `is caused by` / `causes` |
| `jira.comments` | incident.jira | real comment array (else the server synthesizes one) |
| `pagerduty.related_incidents` | incident.pagerduty | list of PagerDuty ids |
| `links` / `parent_id` | confluence page | page ids, Jira keys, and/or commit shas |
| `world.deploys` | world | `[{id, service, sha, at, channel, thread_ts, message, permalink}]` |
| `world.oncall_rotations` | world | `{team: [{person, start, end}]}` |

## The git history

`sim/repo`'s commit log stays: `initial services` (original 4 services only -- its tree must stay
byte-identical, so it is built from a fixed list of the original service names, never from
`world["services"]`, which by generation time also holds the 11 new ones) -> the original 10
incident commits, in order (unchanged shas) -> **`add new services`** (writes the 11 new service
directories and the full, updated `CODEOWNERS`, dated the day before the first new incident's own
commit) -> the 40 new incident commits, in chronological order (not necessarily `INC-id` order --
a repeat pair's second incident can land after the next pair's first incident starts). Committing
strictly in date order matters: `git log --since/--until` assumes date-ordered history and can
silently truncate a path's log if an out-of-order commit sits in the middle of it.

A few Slack messages and Jira comments are written before the commits they mention exist yet
(a red herring names *another* incident's future sha; a postmortem lists *two* incidents' shas).
Those are written as `{{SHA:INC-0NN}}` / `{{SHA10:INC-0NN}}` placeholders and resolved by one
generic pass in `build_repo()` once every commit is final -- grep `sim/data/world.json` for `{{` if
you ever suspect one leaked through; there should be none.

## A few starting points

- `INC-011` (`AUTH-106`) walks the richest single path: cascade upstream, red-herring
  overlay's neighbor, and a Jira-comments overlay target, all in one ticket.
- `channel_id=C542575C5, thread_ts=1789642140.020000` -- `INC-011`'s `#incidents` thread -- is a good
  `investigate-slack-thread` input that will pull in two downstream incidents' team-channel threads
  by permalink (re-derive the thread_ts from a fresh `world["incidents"][10]["slack"]` if you
  regenerate with a different seed).
- `AUTH-117` / `AUTH-122` (`INC-026`/`INC-027`) plus postmortem page `50021` is the cleanest
  `investigate-jira-ticket` walk into "have we seen this before".
- `SSO-112` (`INC-038`) demonstrates the team-channel-to-#incidents escalation permalink pair.
- `#deploys` (`world["channels"]["#deploys"]`) is a good target for a flow that wants "what shipped
  right before this incident".

## Regenerating

```bash
uv run python sim/world.py            # sim/data/world.json + sim/repo (gitignored, regenerated)
uv run python sim/build_catalog.py    # catalog/entities.yaml
uv run pytest -q tests/test_sim_scenarios.py
```

`tests/test_sim_scenarios.py` checks: the first 10 incidents / 4 services / 8 people / 10 channels /
8 pages stay byte-identical to `main`; the first 11 git commit shas stay unchanged and every new
commit exists and comes after them; every archetype's specific cross-links (issuelinks, related
incidents, escalation/deploy/repeat consistency, on-call assignment); no dangling ids; the new part
of the entity graph has no isolated island; regenerating the world twice is byte-for-byte identical;
and the servers actually serve the new fields end to end.
